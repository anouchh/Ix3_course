## 2. Постановка задачи и контекст

### Предметная область и задача

HR-менеджер компании хочет заранее выявлять сотрудников, которые планируют уволиться, чтобы своевременно принять меры: предложить повышение, скорректировать нагрузку, провести беседу. Без инструмента прогнозирования это делается интуитивно и часто слишком поздно.

### Формулировка задачи в терминах ML

- **Входные данные:** профиль сотрудника (возраст, зарплата, стаж, удовлетворённость, сверхурочная работа и др. — 30 признаков)
- **Целевая переменная:** `Attrition` — уволился (1) / остался (0)
- **Тип задачи:** бинарная классификация
- **Требования:** высокий Recall по классу "уволился" — важнее не пропустить сотрудника в зоне риска, чем избежать ложной тревоги

### Целевые метрики

- **ROC-AUC** — основная метрика; устойчива к дисбалансу классов (84% / 16%),
показывает способность модели различать классы
- **Recall (уволился)** — доля реально уволившихся, которых модель нашла;
  приоритетна для HR-задачи

## 3. Данные

### Источник

IBM HR Analytics Employee Attrition Dataset (Kaggle, открытые данные):
https://www.kaggle.com/datasets/pavansubhasht/ibm-hr-analytics-attrition-dataset

Датасет синтетически сгенерирован IBM, не содержит персональных данных.

### Структура данных

- Файл: `data/WA_Fn-UseC_-HR-Employee-Attrition.csv`
- 1470 строк (сотрудников), 35 признаков
- Признаки: числовые (возраст, зарплата, стаж) и категориальные
  (отдел, должность, семейное положение, сверхурочные)
- Целевая переменная: `Attrition` (Yes / No)

### Предобработка и EDA

Шаги предобработки (`notebooks/01_eda.ipynb`):

1. Удалены бесполезные колонки с одним значением у всех сотрудников:
   `EmployeeCount`, `Over18`, `StandardHours`, `EmployeeNumber`
2. Пропусков не обнаружено
3. Категориальные признаки закодированы фиксированными маппингами
   (не LabelEncoder — во избежание различий кодировки при инференсе)
4. Стратифицированный split: train 80% / test 20%

**Ключевые наблюдения из EDA:**
- Дисбаланс классов: 84% остались, 16% уволились — решён через `class_weight='balanced'`
- Сотрудники с низкой зарплатой уходят значительно чаще
- Сверхурочная работа (`OverTime: Yes`) резко повышает вероятность увольнения
- Высокая удалённость от работы и частая смена работ — дополнительные факторы риска

## 4. Модели и подходы

### Базовые модели

**Логистическая регрессия** (Pipeline: StandardScaler + LogisticRegression):
- Масштабирование необходимо — признаки имеют разные диапазоны (зарплата vs возраст)
- `class_weight='balanced'` для работы с дисбалансом классов
- ROC-AUC: 0.807, Recall: 0.77

**Decision Tree:**
- Простое дерево без ограничений глубины
- Ожидаемо переобучилось: ROC-AUC 0.572

### Улучшенные модели и эксперименты

**Random Forest** (100 деревьев, `class_weight='balanced'`):
- Базовый: ROC-AUC 0.757, Recall 0.09 — плохо ловит уволившихся
- С подбором гиперпараметров через GridSearchCV
  (max_depth, n_estimators, min_samples_leaf, cv=5):
  лучшие параметры `max_depth=None, min_samples_leaf=1, n_estimators=200`
  — ROC-AUC вырос до 0.786, но Recall остался низким (0.09)

**LightGBM** (`class_weight='balanced'`, `learning_rate=0.05`, `max_depth=5`):
- ROC-AUC 0.787, Recall 0.38
- Лучше Random Forest, но значительно хуже логрегрессии по Recall

## 5. Экспериментальный протокол и результаты

### Протокол

- Разбивка: train/test = 80%/20%, стратифицированная по целевой переменной
- Метрики считались на тестовой выборке (294 сотрудника)
- Для Random Forest использовалась 5-fold кросс-валидация при подборе гиперпараметров

### Сравнение моделей

| Модель | ROC-AUC | Recall (уволился) | Комментарий |
|--------|---------|-------------------|-------------|
| Логистическая регрессия | **0.807** | **0.77** | Финальная модель |
| LightGBM | 0.787 | 0.38 | Переобучение на малых данных |
| Random Forest (tuned) | 0.786 | 0.09 | Почти не находит уволившихся |
| Decision Tree | 0.572 | 0.30 | Сильное переобучение |

### Выбор финальной модели

**Финальная модель: Логистическая регрессия**

Логрегрессия лидирует по обеим ключевым метрикам: ROC-AUC 0.807 и Recall 0.77.
Более сложные модели (LightGBM, Random Forest) переобучились на небольшом датасете
(1470 строк) — классический случай, когда простая модель выигрывает у сложной.
Для HR-задачи Recall критичнее точности: лучше ложная тревога, чем пропущенный
сотрудник. По этому критерию логрегрессия вдвое лучше LightGBM.

## 6. Архитектура решения и сервис

### Архитектура пайплайна

```
Входной JSON (профиль сотрудника)
        ↓
preprocessor.py — кодирование категориальных признаков
        ↓
predictor.py — загрузка model.pkl, StandardScaler + LogisticRegression
        ↓
Выходной JSON: {attrition_probability, risk_level}
```

### API и эндпоинты

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/health` | Возвращает `{"status": "ok"}` |
| POST | `/predict` | Принимает профиль сотрудника (30 признаков), возвращает вероятность и уровень риска |

Уровни риска: `low` (< 0.35), `medium` (0.35–0.60), `high` (> 0.60)

### Технологический стек

- **FastAPI** — веб-фреймворк для API
- **Pydantic** — валидация входных данных
- **scikit-learn** — модели и предобработка
- **joblib** — сериализация модели
- **uv** — управление зависимостями
- **Docker** — контейнеризация сервиса

Запуск: см. `README.md`, разделы 4.1 и 4.2.

## 7. Наблюдаемость, конфигурация и безопасность

### Логи и наблюдаемость

- Каждый запрос к `/predict` логируется: входные данные и результат предсказания
- Каждый ответ сервиса логируется с уровнем `INFO`
- Эндпоинт `/health` позволяет проверить работоспособность сервиса
- Уровень логирования настраивается через переменную окружения `LOG_LEVEL`

### Конфигурации

Параметры вынесены в переменные окружения (шаблон в `configs/.env.example`):
- `APP_HOST`, `APP_PORT` — адрес и порт сервиса
- `LOG_LEVEL` — уровень логирования
- `MODEL_PATH` — путь к файлу модели

### Безопасность

- Реальный `.env` добавлен в `.gitignore` — в репозиторий не попадает
- Датасет открытый, не содержит персональных данных
- Секретов и токенов в коде нет

## 8. Ограничения и дальнейшая работа

**Текущие ограничения:**
- Датасет синтетический (IBM) — реальные данные компании могут существенно отличаться
- Модель статична — не переобучается при появлении новых данных
- Нет мониторинга дрейфа данных и деградации качества в продакшне
- Нет объяснения предсказаний для конкретного сотрудника (SHAP не реализован)

**Дальнейшие шаги:**
- Добавить SHAP-объяснения: какие признаки повлияли на предсказание
- Настроить автоматическое переобучение модели при поступлении новых данных
- Добавить мониторинг метрик качества через Prometheus/Grafana
- Реализовать хранение истории предсказаний в базе данных

## 9. Сценарий демонстрации на защите

**Запускаю:**
1. Сервис через Docker: `docker run -p 8000:8000 hr-attrition`
2. Демонстрационный скрипт: `python demo.py`

**Два ключевых сценария:**
1. **Сотрудник в зоне риска** — молодой, низкая зарплата, сверхурочные, низкая
   удовлетворённость → высокая вероятность увольнения, риск `high`
2. **Стабильный сотрудник** — опытный, высокая зарплата, нет сверхурочных,
   высокая удовлетворённость → низкая вероятность, риск `low`

**Обращу внимание преподавателя на:**
- Логи сервиса — каждый запрос логируется с результатом
- Таблицу сравнения моделей в ноутбуке — обоснование выбора логрегрессии
- Структуру кода — разделение на `data/`, `models/`, `service/`

Команды запуска описаны в `README.md`.
