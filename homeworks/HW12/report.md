# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано

* Датасет: `S12-hw-dataset.csv`.
* Прогнозировалась колонка `target` на один шаг вперёд (`horizon = 1`).
* Выполнен корректный `train / validation / test` split **по времени**, без перемешивания.
* Реализованы baseline-подходы:

  * `B1`: naive-last,
  * `B2`: moving-average,
  * `B3`: Ridge на лаговых и календарных признаках.
* Реализована нейросетевая модель:

  * `R1`: GRU.
* Лучшая модель выбиралась по `validation MAE`.
* `test` использовался ровно один раз — только для финальной оценки лучшего подхода.

## 3. Данные и постановка задачи

* Датасет: `S12-hw-dataset.csv`
* Целевая переменная: `target`
* Частота временного ряда: почасовая
* Горизонт прогноза: `1`
* Размер датасета: **4320 наблюдений**
* Диапазон дат: **2025-01-01 — 2025-06-29**
* Дополнительные признаки: отсутствуют (используются только производные признаки)

### Анализ ряда

Временной ряд демонстрирует выраженную сезонность, связанную с часами суток и днями недели.
Наблюдаются регулярные колебания, характерные для периодических процессов.
Явного выраженного тренда не наблюдается, уровень ряда остаётся относительно стабильным.
Пропусков в данных нет, что упрощает построение моделей.

## 4. Temporal split и признаки

### 4.1 Разбиение по времени

Использовано последовательное разбиение:

* train: 70%
* validation: 15%
* test: 15%

### Почему random split некорректен

При случайном перемешивании модель получает доступ к будущим данным во время обучения.
Это приводит к утечке информации и нереалистично хорошим результатам.

Для временных рядов корректная постановка задачи —
**обучение на прошлом → предсказание будущего**, поэтому используется только temporal split.

---

### 4.2 Признаки

Использованы следующие признаки:

**Лаговые:**

* lag_1, lag_7, lag_14
* дополнительно: lag_24, lag_168

**Rolling-признаки:**

* rolling_mean_7, rolling_std_7
* дополнительно: rolling_mean_24, rolling_std_24

**Календарные:**

* dayofweek, hour, day, month, is_weekend

### Обработка пропусков

После построения лагов и rolling-признаков первые строки содержат `NaN`.
Они были удалены с помощью `dropna()`.

### Масштабирование

* Для `B3`: `StandardScaler` по признакам (обучение только на train)
* Для `R1`: `StandardScaler` по target (обучение только на train)

Это предотвращает утечку информации.

## 5. Модели и эксперименты (B1, B2, B3, R1)

Опишите коротко и сопоставимо:

- **B1 (`naive-last`)**: наивный baseline, в котором прогноз для момента времени `t` равен последнему известному значению ряда, то есть `target[t-1]`. Эта модель не требует обучения и задаёт минимальный ориентир качества.
- **B2 (`moving-average`)**: baseline на основе скользящего среднего по окну разумного размера. В работе использовалось окно длины `24`, то есть прогноз строился как среднее по предыдущим 24 наблюдениям.
- **B3 (`ridge-lag-features`)**: модель `Ridge` на лаговых, rolling- и календарных признаках. Для неё использовались признаки `lag_1`, `lag_7`, `lag_14`, `rolling_mean_7`, `rolling_std_7`, а также дополнительные признаки `lag_24`, `lag_168`, `rolling_mean_24`, `rolling_std_24`, `dayofweek`, `hour`, `day`, `month`, `is_weekend`.
- **R1 (`gru-forecast`)**: модель `GRU` на оконном представлении ряда. На вход подавалось окно длины `48`, а модель предсказывала следующее значение ряда.

Дополнительно:

- **Основная метрика выбора лучшей модели:** `MAE` на `validation`
- **Дополнительные метрики:** `RMSE`, `MAPE`, дополнительно считалась `sMAPE`
- **`window_size` для `GRU`:** `48`
- **Batch size:** `128`
- **Максимальное число эпох:** `25`
- **Optimizer:** `Adam`
- **Learning rate:** `1e-3`
- **Как сохранялась лучшая модель:** сохранялся `state_dict()` лучшего checkpoint по минимальному `validation MAE` в файл `./artifacts/best_gru.pt`

## 7. Анализ

Наивная модель (B1) задаёт базовый уровень качества, но не учитывает сезонность.
Moving average (B2) сглаживает шум, однако теряет важные динамические изменения.

Модель Ridge (B3) показала наилучшие результаты благодаря тому, что:

* использует лаговые признаки,
* учитывает сезонность,
* включает календарную информацию.

GRU (R1) не смогла превзойти Ridge. Возможные причины:

* относительно небольшой объём данных,
* зависимости хорошо описываются простыми признаками,
* нейросеть избыточна для данной задачи.

Результаты на validation и test близки, что говорит об отсутствии переобучения.

---

## 8. Итоговый вывод

Для данного датасета классический подход с лаговыми и календарными признаками оказался наиболее эффективным.

Преимущества baseline-подхода:

* простота реализации,
* высокая интерпретируемость,
* лучшее качество на данной задаче.

GRU может быть полезна:

* при более сложных временных зависимостях,
* при большем объёме данных.

Главный вывод:
**корректный temporal split и отсутствие утечек важнее выбора модели.**
